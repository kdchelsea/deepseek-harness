# Agent Note：轨迹中的服务商 API 请求

Status: implemented

[English](2026-09-10-trajectory-request-input.md) | 中文

## 问题

Session 消息与请求头可以还原服务商无关的输入，但不能还原经过适配器默认值、扩展字段、图片上传及服务商格式转换后的最终 API 请求体。

## 决策

适配器在发送前通过 `llm/request-body` 发布序列化 JSON。轨迹 Host 插件将普通请求关联到活跃的助手尝试，将请求体保存为附件，并在模型表面之外持久化 `trajectory/request` 文件引用。输入页通过现有 Session 分页读取所选步骤最近的请求体。不包含 HTTP 请求头。DeepSeek 捕获序列化后的 fetch 请求体；pi-ai 转发服务商请求体回调，不替换请求体。

## 考虑过的替代方案

**重新序列化历史消息。** 当前适配器配置、扩展状态和已上传图片标识可能与原始请求不同，结果不能证明实际发送的内容。

**仅在内存中保留请求体。** 刷新或重新打开 Session 后将丢失所需的检查数据。

## 影响

完整请求体增加附件存储量，包括内联图片与服务商扩展字段。日志只保留文件引用，避免服务商的 Session 日志扩展递归嵌套旧请求体。未采集的旧请求和辅助请求仍不可用。每次发送都会保留，步骤检查器展示最近的请求体。[请求可还原决策](../architecture/2026-07-05-reconstructable-requests.zh.md)仍约束模型输入；诊断请求体不会进入派生消息。采集随 Web 轨迹插件安装，在插件卸载时停止。两种适配器的测试将捕获的 JSON 与本地 HTTP 服务收到的请求体对比；历史浏览器夹具验证不可用状态。

请求检查器也通过现有轨迹投影展示关联的模型结果。复用已记录的内容块可保留思考、工具调用与实时更新，无需引入第二份响应日志；不会重建服务商 HTTP 响应封装。已加载窗口之外的结果明确显示为不可用。

原始响应检查将已收到的 HTTP 正文作为独立的 `trajectory/response` 附件引用持久化，包括失败响应和中断前缀。适配器负责在解析前采集，并在结束尝试前等待发布，因此取消不会丢弃已收到的文本。客户端按步骤顺序展示每次响应，不会将组装后的内容当作服务商原始 JSON。仅采集 HTTP 避免全局 fetch 拦截，并保持不支持的传输行为不变。

结构化检查仅为展示解析已保存的正文。受维护的 SSE 解析器提供完整事件；注释和未完成的帧仍可在原文视图查看。折叠的事件行不挂载 JSON 树，因此较长的 token 流不会安装隐藏的字段树监听器。附件仍是服务商原始文本的权威来源。
